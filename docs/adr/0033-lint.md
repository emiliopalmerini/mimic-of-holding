# ADR-0033: Deterministic vault lint

## Status

Proposed

## Context

The vault grows by hand-edits, by `mimic` mutations, and (soon) by an `ingest` skill. Drift is inevitable: a folder gets renamed but the JDex file is forgotten, a wiki link points at a moved page, a numbering gap appears when an item is archived. These are mechanical errors a deterministic checker can flag faster and more reliably than the LLM can reason about.

Per the LLM-as-librarian principle established in the vault's `CLAUDE.md`, the LLM never auto-fixes. `mimic lint` produces a **report only**: it identifies issues, the user (with or without LLM assistance) decides what to fix.

A separate, future skill will handle non-deterministic checks (contradictions, stale claims, missing concept pages). This ADR covers only the mechanical layer.

## Decision

Add a `lint` command to the CLI that performs deterministic structural checks against the vault and emits a markdown report.

### Command shape

```
mimic lint [scope]
```

- `scope` (optional): one of `S01`, `S02`, `S03`. When omitted, the whole vault is linted.

**Output:** a markdown report on stdout, organized into H2 sections (one per check category). Sections with zero findings are elided. Empty report (i.e. no issues) prints a single line: `No issues found.`

**Exit code:**
- `0` — no issues found
- `1` — at least one issue found
- `2` — input/runtime error (invalid scope, missing vault, etc.)

### Auto-log behavior

When `mimic lint` is invoked with a specific scope, the run auto-logs to that scope's `log.md` after producing the report. The entry uses op `lint` with details summarizing findings:

```markdown
## [2026-05-07 14:30] lint | S01

5 issues across 3 categories: 2 missing-jdex, 2 broken-frontmatter, 1 numbering-gap.
```

Whole-vault lint (`mimic lint` with no arg) does **not** auto-log, since there is no single canonical scope to write to. The LLM/user can manually `mimic log append` per scope if they want to record a multi-scope sweep.

### Check categories

The checker runs the following deterministic checks. Each issue carries a category, a reference (JD ref or relative path), and a one-line detail.

| Category               | What it flags                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| `missing-jdex`         | An ID folder with no JDex file matching the folder name.                                                   |
| `broken-frontmatter`   | A JDex file missing one or more required fields: `aliases`, `location`, `tags` (with `jdex` and `index`).  |
| `name-mismatch`        | A `.md` file whose stem matches the folder pattern `S0X.YY.ZZ` but does not match the actual folder name.  |
| `numbering-gap`        | Within a category, a missing ID number between two existing regular IDs (e.g. `.11`, `.12`, `.14` skips `.13`). Standard zero range `.01`–`.09` is excluded. |
| `broken-link`          | A `[[Target]]` (or `![[Target]]`) reference whose target name is not a known file or alias in the vault.   |
| `orphan-id`            | An ID whose folder name (or any of its aliases) appears in no other file's `[[link]]` set. Standard zero IDs (`.01`–`.09`) are excluded. |

### Report format

```markdown
# Lint Report — S01

## missing-jdex (2)
- `S01.11.99 Foo`: folder has no JDex matching its name
- `S01.21.14 AI Patterns`: folder has no JDex matching its name

## broken-frontmatter (1)
- `S01.11.11 Theatre, 2025 Season.md`: missing `aliases`

## numbering-gap (1)
- `S01.11`: gap at `.13` (between `.12` and `.14`)

## broken-link (1)
- `S01.11.11/notes.md`: `[[Missing Page]]` does not resolve

## orphan-id (1)
- `S01.21.14 AI Patterns`: not referenced by any `[[link]]`
```

Section headers carry the issue count in parentheses. Items are markdown bullets with the affected reference in code spans, then a colon-separated detail.

For whole-vault lint, the H1 is `# Lint Report — All scopes` and findings stay flat (no per-scope grouping); each item's ref already encodes its scope.

### Domain functions

In `internal/vault/`:

```go
// LintIssue describes a single finding.
type LintIssue struct {
    Category string // see check categories above
    Ref      string // JD ref or relative path
    Detail   string // human-readable description
}

// LintResult is the aggregate output of a lint pass.
type LintResult struct {
    Scope  string       // "S01" or "" for whole-vault
    Issues []LintIssue
}

// Lint runs all deterministic checks. If scope is non-empty, only that scope
// is examined. Returns a result whose Issues slice may be empty.
func Lint(v *Vault, scope string) (*LintResult, error)

// FormatLintReport renders a LintResult as the markdown report described in
// this ADR.
func FormatLintReport(r *LintResult) string
```

Internally, each check is a small function that walks the relevant subtree and appends issues to a shared slice. Checks are independent and can be added or removed without affecting the others.

### Wiki link resolution

For `broken-link`, the resolver builds an index from:

- every `.md` file's stem (without extension), keyed by stem;
- every `aliases:` entry parsed from frontmatter;
- every directory name that matches a JD folder pattern.

A link `[[Target]]` (with optional `|alias`, `#heading`, `^block`) is normalized: drop everything from the first `|`, `#`, or `^`; if the remainder contains `/`, take the last segment. The resulting head is looked up in the index. If not found, the link is flagged.

Embeds (`![[Target]]`) are checked the same way. Internal anchors (e.g. `[[#Heading]]` with empty head) are skipped (resolve to current file).

### Orphan detection

For `orphan-id`:

- The set of all `[[X]]` heads across the vault is collected.
- For each ID in scope (excluding standard zeros `.01`–`.09`), if neither the folder name nor any frontmatter alias is in the set, the ID is flagged.

This is intentionally conservative — an ID linked only from outside the vault, or referenced through Dataview queries, will appear orphan. Acceptable for a v1; the user can ignore false positives or add an alias to suppress them.

### Edge cases

- **Empty vault / scope with no IDs**: returns an empty result; report prints `No issues found.`
- **Invalid scope arg** (e.g. `S99`): exit code 2 with stderr error.
- **Unreadable file** (permission error mid-walk): the lint pass aborts with exit code 2; partial findings are not emitted. Rationale: a failed walk produces an unreliable orphan/broken-link index.
- **Code blocks containing `[[...]]`**: not stripped in v1. False positives acceptable; the user can mark them or we can add fenced-block stripping later.
- **Dataview queries** that materialize lists of IDs: not parsed. May produce orphan false positives.
- **Standard zero IDs** (`.01`–`.09`): excluded from `numbering-gap` and `orphan-id`. Still subject to `missing-jdex`, `broken-frontmatter`, `name-mismatch`, and `broken-link`.
- **Performance**: link index is built once per run by walking the vault. For typical vault sizes (a few thousand markdown files) this is fast. No incremental linting in v1.

### What is NOT included

- No auto-fix. Findings are reported; the user decides.
- No semantic checks (contradictions, stale claims, missing concept pages, gap suggestions). Those belong to a future LLM-driven skill.
- No frontmatter-schema validation beyond JDex required fields. Specific document-type schemas are out of scope.
- No cross-scope orphan detection (an ID in S01 referenced only from S02 is not orphan; an ID in S01 referenced by nobody is). Cross-scope is already covered.
- No `--fix`, `--strict`, or `--skip <category>` flags in v1. Add later when motivating need appears.
- No JSON output mode in v1. Markdown only.

## Consequences

- A new mutation point in the codebase (`internal/vault/lint.go`). Adding a new check means one new function and one entry in the dispatch list — no refactor needed.
- Lint runs are O(N) over markdown files in the scope. Single-pass walk, in-memory index. Fine for current vault size.
- Auto-log entries on scope-specific lint runs become part of the activity timeline. The LLM can read them via `log tail` to know when the vault was last cleaned.
- Future ADRs can extend lint with new categories without revising this ADR.
